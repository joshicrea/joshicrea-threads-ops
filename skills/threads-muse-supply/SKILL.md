# 供給キット(Muse が投稿案を供給し続ける手順)

読み手は、利用者の PC で動く AI です(Muse・Claude Code・Codex のいずれか)。この手順書のとおりに、定期的に動いてください。

## 1. 全体像

AI プロバイダに Muse を選ぶと、本体は文章を作りません。文章を作るのは、あなた(Muse)です。本体は、あなたが渡した投稿案を承認待ちに置き、利用者が承認したものを、時刻になると Threads へ公開します。予約投稿の公開とトークンの更新は、本体が自分で回します。

あなたの仕事は、次の4つを、決まった間隔で繰り返すことです。

| # | 仕事 | 使う道具 | 間隔の目安 |
|---|---|---|---|
| 1 | 本体に「あなたが動いている」と知らせる | threads_tick(または curl で POST /api/tick) | 15分ごと |
| 2 | 在庫(承認待ち+予約済み)を見る | threads_status の supply | 1の直後 |
| 3 | 在庫が下限に満たなければ、投稿案を書いて足す | threads_add_post | 在庫が足りないとき |
| 4 | 届いたコメントに、返信文の下書きを渡す | threads_list_replies と threads_set_reply | 1日に数回 |

供給が止まると、本体は次の2つのどちらかで気づき、利用者の画面(「今やること」と設定画面)に「Muse からの供給が止まっています」と出します。

- 1 の呼び出しが60分以上ない
- 在庫が下限(設定の「1日の投稿数」)を下回った状態が24時間続いた

提供元から、利用者の PC の中は見えません。止まりを見つけられるのは、利用者の画面と、あなたが threads_status で見る状態だけです。

## 2. 始める前に確かめること

1. `threads_status` が通る(本体が動いている)。通らなければ、利用者に本体の起動(`~/.claude/threads-ops/app/起動.cmd`、Mac は `起動.command`)を頼む。自分では起動しない
2. `ai.provider` が `muse`。違えば、利用者に本体の設定画面(http://localhost:4173)の「AIプロバイダ」で Muse を選んで保存してもらう。保存の前に「このツールは文章を作らなくなります。あなたの AI が供給する設定(供給キット)が必要です」という確認が出る
3. `threads.connected` が true。false なら、先に `skills/threads-setup/SKILL.md` の手順で連携する
4. `threads_get_settings` で、発信者の名前・プロフィール・文体(writingRules)・テーマ(themes)・見せられるもの(materials)を読む。投稿案は、ここに書かれたことだけを題材にする。書かれていない実績・数字・特典を足さない

## 3. 1周期の手順(毎回この順)

1. `threads_tick` を呼ぶ(道具は、必要なヘッダとアクセスキーを自分で付ける。これが基本の呼び方)。HTTP しか使えない場合だけ、次でもよい。`x-threads-ops: 1` のヘッダが無いと、本体は 403 で断る(返りの文に「x-threads-ops のヘッダが付いていない」と原因が出る)。`x-threads-caller: muse` のヘッダが無いと、呼び出しは通っても、本体は「Muse からの接続があった」と数えない。次の例は両方を付けている。

   ```
   curl -s -X POST http://localhost:4173/api/tick -H "x-threads-ops: 1" -H "x-threads-caller: muse"
   ```

   ポートは、本体の画面のアドレスのポート(既定は 4173。`threads_status` の `dashboardUrl` で分かる)に合わせる。アクセスキーを設定している本体では、`-H "x-threads-key: <利用者が決めたキー>"` も付ける。キーの値は、利用者に聞く(チャットや記録に書かない。`db.json` などの設定ファイルを読んで探さない。中に、Threads のトークンなど、あなたに渡してはいけない値も入っている)。返りに `ok: true` が入る。`503` で「起動の途中です」と返ったら、1分あけてもう一度呼ぶ

2. `threads_status` を呼び、`supply` を読む。`supply.stock` が今の在庫(承認待ちと予約済みの合計)、`supply.lowerBound` が下限。`supply.warning` が true なら、`supply.message` を利用者に1行で伝える

3. 在庫が下限に満たなければ(`stock < lowerBound`)、足りない本数だけ書いて足す。

   - 1回に足す本数は、足りない本数(`lowerBound - stock`)まで。下限は、安全確認がONのとき、設定の1日の上限(safetyDailyPostLimit、既定10本)を超えないよう、本体が調整済みなので、足りない本数だけ足せば、1日の上限の範囲に収まる
   - 発信テーマ(`threads_get_settings` の themes)が設定されていれば、有効なテーマ(enabled が false でないもの)を、出す量(weight)の比率で配り、`threads_add_post` の theme にテーマ名を渡す。「N日に1回は必ず」(everyDays)のテーマは、その日数があいていたら先に入れる
   - 1本ずつ `threads_add_post`(text は500字まで、category・topicTag・theme は任意)。返りの `id` を控える。「同じ本文」は、全角半角・大文字小文字・空白・見えない文字の違いを除いて同じものを指す。却下された本文・エラーの本文とも同じとみなして断られる
   - 「同じ本文がすでにあります」で断られたら、別の本文を書き直す。同じ本文を送り直さない
   - 安全確認で止まる内容・案件ルール違反と断られたら、その理由に沿って本文を直して、1回だけ送り直す。2回続けて断られたら、その案は諦めて次の案を書く
   - `scheduledAt`(予約時刻)は、利用者が「あなたが書いた投稿を、承認なしで予約まで進めてよい」と明確に言っているときだけ付ける(自動送信が ON というだけでは、その許可にならない)。付けると、本体が承認と予約まで進める。付けなければ、本体が次の空いている枠の日時を入れて承認待ちに置き、利用者が本文を見て承認する(自動送信が ON なら、承認と同時に予約される)。付けても自動送信が OFF・安全確認や案件ルールで予約できないときは、承認待ちのまま入り、返りの `note` に理由が出る

4. コメントがあれば(1日に数回でよい)、`threads_fetch_replies` のあと `threads_list_replies`(status=unhandled)を読み、返信文の下書きを書いて `threads_set_reply`(responseText)で渡す。送るのは、利用者が本文を見て「送って」と言ったあとの `threads_reply` だけ。自動では送られない。相手をユーザー名で呼ぶ書き方はしない。対応しないコメントは status=ignored

5. 結果を1行で残す(例: 「在庫2→3、足した本数1、tick 済み」)。利用者に聞かれたら、これを答える

## 4. 定期的に動く仕組みを、あなたが持てるか確かめる

この手順書は、あなたが自分で定期的に動けることを前提にしています。動けるかどうかは AI ごとに違うので、最初に1回、次の順に確かめて、利用者に結果を伝えてください。

1. あなたに、時刻や間隔を指定して後で自分を呼び出す仕組みがあるか(スケジュール・定期実行・繰り返しの予約など、名前は問わない)。ある場合は、その仕組みの名前と、使える最短の間隔を利用者に伝える
2. ある場合は、3 の1周期を「15分ごと」(在庫が足りているときは tick だけでよい)で登録する。登録したら、15分あとに `threads_status` の `supply.lastTickAt` が更新されたかを確かめる。更新されていれば、定期実行が動いている
3. 登録しても動かなかった、または最短の間隔が60分より長い場合は、定期的な供給は成立しません。次の「持てない場合」に進む

持てない場合(あなたが自分で定期的に起動できない):

- 利用者が1日に1回以上、あなたに「供給して」と言って起動する運用にする。その1回で 3 の1周期を行う
- この運用では、本体の「Muse からの供給が止まっています」が、次に起動するまでの間に出ることがある(1の呼び出しが60分以上あくため)。出たら、利用者に「定期的な呼び出しがないためです。1日1回の手動運用では出る場合があります」と伝える
- 毎日の運用を自動にしたい利用者には、設定の AI プロバイダを Claude Code・Codex CLI・Gemini API のどれかに切り替えることを案内する。これらを選ぶと、本体が文章を作り、この手順書は要らなくなる

## 5. 止まった(警告が出た)とき

- `supply.message` に「tick が60分以上ありません」とある: 定期実行が止まっています。3 の1周期をいま1回実行し、4 の確認をやり直す
- 「在庫が下限を下回ったまま24時間」とある: 3 の手順 3 で足す。足りない本数が多いときは、1日の上限(safetyDailyPostLimit)の範囲で足し、残りは翌日に回す
- 足しても警告が消えないときは、`threads_status` の `supply.lastTickAt`(1の印)と `supply.stock` を利用者に見せて、プロバイダの切り替えを案内する

## 6. 守ること

- 承認・公開・返信の送信は、利用者が本文を見て明示したときだけ行う。あなたが書いた投稿を、利用者の承認なしに公開しない(`scheduledAt` を付けるのは、利用者が「承認なしで予約まで進めてよい」と明確に言ったときだけ)
- 削除に関わる操作はしない
- パスワード・連携コード・アクセストークン・アクセスキーの値を、チャット・記録・投稿案に書かない
- 本体に何か不具合のような表示が出たら、回避せずに止めて、提供元に知らせてもらう
- 投稿案は、利用者の言葉(プロフィール・文体・見せられるもの)だけから作る。他人の投稿の丸写しをしない
